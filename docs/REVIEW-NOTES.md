## 二、本轮发现的问题

### 2.1 同意好友的身份校验字段用错（严重）

**现象**：为修复"服务端不校验操作身份"（README 第 12 项），在 5 个业务处理函数里加了 `isOwnIdentity()`。
其中 `addFriendAgree()` 校验的是 `caData[0:32]`，但这**不是当前用户**。

**证据链**：

```
客户端 ResHandler::addFriendResend()
    memcpy(respdu->caData, pdu->caData, 64);   // 原样沿用 ADD_FRIEND_RESEND 的 caData
                                               // 内容是 [发起方 A, 同意方 B]
        ↓
服务端 MsgHandler::addFriendAgree()
    caCurName = caData[0:32] = A               // 发起方
    caTarName = caData[32:64] = B              // 同意方 = 本连接登录名
    isOwnIdentity(caCurName)  →  A == B ?      // 恒为 false，一律拒绝
```

**后果**：真实客户端点"同意"永远失败；而手工构造测试包时若字段写反（`[B, A]`）反而会通过。
**这是"实现与测试同时错"的典型形态**，详细分析见 3.1 节。

**修复**：`isOwnIdentity(caTarName)` —— 该校验的是**同意方**（后 32 字节）。

**协议语义对照表**（这是本项目最容易踩的坑，值得记住）：

| 消息 | `caData[0:32]` | `caData[32:64]` | 该校验哪一段 |
|---|---|---|---|
| `CHAT` / `ADD_FRIEND` / `FLUSH_FRIEND` / `DEL_FRIEND` | 当前用户 | 对方 | 前 32 字节 |
| `ADD_FRIEND_AGREE` | **发起方（对方）** | **同意方（自己）** | **后 32 字节** |

根因是客户端复用转发包：`ADD_FRIEND_RESEND` 的 `caData` 是 `[A, B]`，
客户端收到后整段复制再发出，于是"自己"落在了后半段。

### 2.2 `resend()` 读取 32 字节定长字段越界（中）

```cpp
const QByteArray tarName(caTarName);   // QByteArray(const char*) 内部走 strlen
```

`caTarName` 来自 `char x[32]` + `memcpy(..., 32)`。当用户名**恰好 32 字节**时该数组没有 `'\0'`，
`strlen` 会越过栈上 32 字节继续读，属于未定义行为。

**修复**：显式限长构造

```cpp
const QByteArray tarName(caTarName, int(qstrnlen(caTarName, 32)));
```

同样的处理已用在 `isOwnIdentity()` 上。**凡是"定长字段 + 不做 0 填充保证"的组合，都不能当 C 字符串用。**

### 2.3 `migrate_v2.sql` 在它声称支持的旧库上无法执行（中）

脚本首行写着"适用于已经在用旧库"，但第 3 步去重语句用了 `f1.id`，
而**旧版 `friend` 表只有 `(user_id, friend_id)` 两列，没有 `id`**。
执行必然报 `Unknown column 'f1.id'`。

**修复**：在去重前补一列

```sql
ALTER TABLE `friend`
    ADD COLUMN `id` INT NOT NULL AUTO_INCREMENT PRIMARY KEY FIRST;
```

**教训**：迁移脚本的每一条语句都要能在**它声称支持的最老 schema** 上跑通。
写完后应当真的拿一份旧库验证，而不是只在新建库上试。

---

### 2.4 盐使用非密码学随机源（低）

```cpp
raw[i] = char(QRandomGenerator::global()->bounded(256));
```

`global()` 是可预测的伪随机数生成器，不适合生成安全参数。

**修复**：改用 `QRandomGenerator::system()`（由操作系统 CSPRNG 提供）。

**同时保留一个已知局限**：`SHA-256(口令 + 盐)` 只迭代一次，抗离线暴力破解能力弱。
生产环境应使用 PBKDF2 / bcrypt / Argon2 这类带工作因子的算法。
这里作为练手项目接受，但应当知道边界在哪。

## 三、方法论教训

### 3.1 测试与实现同时错，绿灯不证明正确

这是本次最有价值的发现。

**错误链条**：

1. 实现假设 `caData[0:32]` 是当前用户
2. 测试脚本按同一假设手写数据，把同意方放在前面（`[B, A]`）
3. 于是实现与测试**共享了同一个错误前提**
4. 结果：18 项断言全绿，真实客户端却无法完成"同意好友"

**为什么测试没能兜住**：测试数据不是从真实调用方产生的，而是**按照对协议的（错误）理解手搓的**。
手搓的数据只能验证"实现符合我的理解"，不能验证"我的理解符合协议"。

**可复用的做法**：

- 涉及协议字段的测试，**数据应当从真实客户端的发包代码抄**，而不是凭文档臆造
- 同一个字段有多个语义时，写一张对照表贴进文档（见 2.1 节）
- 修复后用**真实 GUI 走一遍流程**，不要只信自动化

> 补充：本次修复 `addFriendAgree` 后，发起方 A 会收到一条同意通知，
> 而测试原先没有预期这个包，导致后续用例读包错位（3 个断言失败）。
> 这说明**修好一处会暴露下一处的假设错误**——绿灯转红不一定是回归，可能是暴露了隐藏问题。

### 3.2 "看起来可疑"与"确实错了"要分开

复查中踩过两个方向的坑：

- **误判为 bug**：`caTarName == m_strLoginName` 曾被断言"比较的是裸指针地址，条件恒为 false"。
  实际上 Qt 提供了 `operator==(const char*, const QString&)` 重载，做的是**内容比较**，逻辑正确。
  已修正文档与注释，并改成显式 `QByteArray` 比较消除歧义（保留其健壮性价值）。
- **漏判**：`QByteArray(caTarName)` 的越界读在类型转换处不起眼，只有想到"定长字段可能没有终止符"才会发现。

**结论**：code review 里"可疑"要写成**建议**，只有能复现的才写成**缺陷**。
README 第九节的措辞已按此调整。

环境：Windows + Qt 5.14.2（MinGW 7.3.0）+ MySQL 5.7，服务端独立进程。

| 脚本 | 覆盖内容 | 本次结果 |

| `tests/test_heartbeat.ps1` | 心跳应答、重复登录互踢、异常掉线超时回收 | **6 / 6**（含 45s 用例时 8/8） |

## 六、可复用的排查清单

下次改协议或加安全校验时，按这个顺序过一遍：

1. **字段语义表**：这个 `caData` 的每一段分别是谁？和同类消息一致吗？
2. **定长字段**：有没有保证 `'\0'` 结尾？没有就必须限长读取，不能当 C 字符串用。
3. **真实调用方**：测试数据是从客户端发包代码抄的，还是手搓的？
4. **双端一致性**：两份 `protocol.h` 是否逐字节相同？枚举是否只追加不插队？
5. **生命周期**：`malloc/free`、`write()` 拷贝语义、`deleteLater` 时机是否说清？
6. **迁移脚本**：能否在最老的 schema 上跑通？
7. **验证手段**：能不能用真实进程跑一遍，而不是只做静态推断？

## 七、面试可讲的三段故事

这三段都来自真实排查，有完整链条，比罗列功能更有说服力。

### 故事一：实现与测试同时错（推荐主讲）

> 我加身份校验后发现"同意好友"会失败。查下来这条消息的 `caData` 语义和其它四类不同——
> 它是 `[发起方, 同意方]`，客户端原样沿用转发包再补自己，所以当前用户在后 32 字节。
>
> 更麻烦的是**我的测试反而通过了**，因为测试脚本手写数据时把两个字段写反了。
> 这是典型的"实现和测试共享同一个错误前提"——绿灯不能证明对，只证明一致。
> 最后靠对照真实客户端的发包路径才发现。
>
> 教训：涉及协议字段的测试，数据必须从真实调用方产生，不能按文档手搓。

### 故事二：互踢引起在线状态被覆盖

> 重复登录踢人时，新连接把 `online` 置 1，紧接着旧连接的 `disconnected` 回调
> 无条件把 `online` 置 0，结果人明明在线、数据库却是离线。
>
> 最初的修法是给被踢连接打标记，后来改成"断线时先判断该账号是否还有其它有效在线连接"——
> 后者更通用，顺带覆盖了"用户开两个客户端"这种历史上没约束的情况。

### 故事三：端口探测的时序陷阱

> 本机空闲端口，程序却报"端口被占用"。排查发现异步 `ConnectionRefusedError` 在
> Windows 上要约 4 秒才送达，而我用 2 秒超时兜底，把"还没连上"误判成"已被占用"。
>
> 改成同步 `waitForConnected(500)`，用"连接成功/失败"这个确定的状态变化替代"等多久"的时间猜测。
> 收获：**用时间做判断条件是脆弱的，要尽量依赖确定的状态转移。**

## 八、维护约定

- 新增业务消息时，先更新两份 `protocol.h` 的**末尾**（枚举只追加），再改两端处理
- 新增涉及文件的操作时，路径必须过 `isSafePath()`，并把登录名以 `m_loginName` 为准，不信 `caData`
- 新增"携带当前用户"的消息时，明确它是前 32 字节还是后 32 字节，并同步更新本文 2.1 节的对照表
- 改动测试脚本后确认 **BOM 仍在**（否则 PowerShell 5.1 解析失败）
